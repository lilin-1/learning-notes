A mechanism that records a sequence of [[kernel|kernels]] on a [[graphics processing unit|GPU]], together with their arguments, and afterwards replays the whole sequence. Normally the CPU issues launch commands one by one; once the sequence is recorded as a graph, a single command replays it. Tensor shapes and memory addresses are fixed at recording time, so each batch size needs a graph of its own.

Note: What it saves is launch overhead. Each kernel launch costs a few microseconds on the CPU side. When each step processes little data, as when tokens are generated one at a time, each kernel runs only briefly and the GPU often sits waiting for the next command, so launch overhead becomes the bottleneck. For compute-heavy steps the overhead is relatively small. The costs are threefold: recording slows startup, every graph takes memory, and a batch size that was not recorded must be padded to a larger one that was, computing a few empty slots.

Example: Suppose a small model launches 480 kernels per decoding step, each needing only 3 microseconds on the GPU, while the CPU takes 5 microseconds to issue each launch. The GPU can only wait for commands, so a step takes about $480 \times 5 = 2400$ microseconds; replaying a graph runs the kernels back to back, about $480 \times 3 = 1440$ microseconds per step, 40% less time.
