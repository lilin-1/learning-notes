# How is a thread block assigned to the hardware and executed?

By resources. Before the GPU's distribution unit sends a [[thread block]] to a [[streaming multiprocessor]], it checks the resources the block needs: registers, shared memory, warp slots and a block slot. Only if all four suffice does the block become resident, and it stays until all its threads have finished; whichever resource runs out first determines how many blocks an SM can hold at once.

Once a block is resident, its threads are grouped 32 at a time into [[warp|warps]], which are spread over the SM's 4 partitions. Every cycle, the scheduler of each partition picks a ready warp and issues its next instruction. A warp reading GPU memory waits hundreds of cycles, and meanwhile the scheduler issues other warps; the more warps are resident, that is, the higher the [[occupancy]], the more easily latency is hidden. Memory accesses pass through the [[memory hierarchy]]: first L1, then the L2 cache, and finally GPU memory.

When a block finishes, the resources it held are released at once, and the distribution unit sends the next block, until every block of the grid has been sent.

Example: Suppose each block has 256 threads, each thread uses 64 registers and each block uses 48 KB of shared memory. An A100 SM then holds 3 blocks at once, 24 warps in all, for an occupancy of $24 / 64 = 37.5\%$. Cutting the shared memory to 32 KB lets 4 blocks fit, raising the occupancy to 50%.
